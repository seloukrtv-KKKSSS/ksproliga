# Статистика гравців

Публічний розділ «Статистика гравців» замінює «Бомбардири». Старі посилання `/?section=scorers` продовжують працювати. У списку є гравці з хоча б одним голом, жовтою або червоною карткою. Доступні пошук, фільтр команди та сортування за кожним показником.

## Як працювати в адмінці

1. Виберіть турнір і команду. У «Склад команди» вставте імена, по одному на рядок, та збережіть.
2. Гравці автоматично з’являться в «Статистика гравців», включно з нульовими показниками. Пробіли й регістр не створюють дублікати в межах команди й турніру. Для двох різних людей з однаковим ім’ям використовуйте різні повні імена.
3. Знайдіть гравця, натисніть «Редагувати» й укажіть загальну кількість голів, жовтих та червоних карток. Ім’я та команда наявного запису захищені від зміни, щоб зберегти зв’язок з історією.
4. У подіях матчу вибирайте ім’я з підказок складу. Для завершеного матчу без технічної поразки додавання й видалення подій автоматично змінює підсумки. Для нового імені створюється запис гравця.

Ручні значення — це поточні загальні підсумки. Не потрібно ще раз додавати до них уже внесені події. Наступні зміни подій змінять ці підсумки на відповідну різницю. Лічильники не можуть стати від’ємними.

Автогол не збільшує кількість забитих голів гравця. `yellow_red` означає другу жовту й додає одну жовту та одну червону. Першу жовту за потреби внесіть окремою подією. Зміна статусу матчу на незавершений або технічну поразку вилучає його внесок; повернення статусу відновлює його.

Повторне збереження складу зберігає ID й статистику гравців. Вилучення імені зі складу зберігає його профіль та історичні підсумки. Видалення гравця заблоковано, доки він є у складі або має події матчів. Перейменування команди переносить її пов’язані записи в межах поточного турніру.

## Оновлення бази

Перед розгортанням коду застосуйте `supabase/migrations/20261110192206_player_statistics.sql` через авторизоване підключення власника бази, звичайний процес міграцій або SQL Editor Supabase. Міграція виконується однією транзакцією та використовує чинні RLS-права організаторів. Локальні SQL-перевірки виконуються на ізольованому PostgreSQL через PGlite.

Спочатку виконайте `scripts/preflight-player-statistics-production.sql`: цей скрипт лише читає дані та показує дублікати нормалізованих імен, стан потрібних таблиць, стовпців і наявні тригери. До міграції усуньте дублікати гравців або команд у межах одного турніру й перевірте сторонні тригери, які вже змінюють статистику.

Після міграції виконайте `scripts/verify-player-statistics-production.sql`. Він перевіряє створення гравців зі складу, збереження ручних підсумків, голи й картки, розділення турнірів і права доступу. Тестові записи створюються в підлеглій транзакції, яка відкотиться як після успіху, так і після помилки; додатковий зовнішній `ROLLBACK` прибирає локальні налаштування. Жодні наявні спортивні записи або профілі організаторів не змінюються. Послідовності ID можуть мати пропуски. Для перевірки реальних RLS-прав використовуються наявні активні адміністратор і організатор; відсутню роль скрипт позначає як пропущену перевірку.

Міграція імпортує наявні склади й гравців із подій матчів. Під час початкового перенесення для голів використовується більше з двох значень: внесений підсумок або кількість зафіксованих голів. Вони не додаються один до одного. Картки переносяться з подій завершених матчів без технічних поразок.

Якщо в базі вже є кілька записів одного нормалізованого імені в одній команді та турнірі, унікальний індекс зупинить міграцію й транзакція відкотиться. Об’єднайте такі записи вручну зі збереженням потрібної статистики та ID перед повторним запуском. Міграція не видаляє ці записи автоматично.

Перевірки: `pnpm test:players`, `pnpm test:players:sql`, `pnpm check`. SQL-тести працюють локально без доступу до робочих даних.
